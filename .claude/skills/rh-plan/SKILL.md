# rh-plan, 계획 단계

**실행 모드: 서브에이전트 위임.**

한 작업(`<id>`)의 구현 계획을 **생성-비평 루프**로 다듬어 승인 가능한 상태로 만든다. 코드는 건드리지 않는다. 산출은 `docs/ai/plan/<id>.md` 와 `docs/ai/plan-critique/<id>.md` 뿐이다.

## 절차

### 0. 컨텍스트

- `<id>` 를 파악한다. 없으면 사용자에게 묻는다.
- **범위 선분리.** 요청을 앱 코드 / 백엔드 / 웹 세 갈래로 나눠 한 줄로 확인한다. 앱 밖 항목은 계획 §2 Non-goals 로 간다. 백엔드 쪽은 **서버 변경 요청**으로 분리해 적는다.
- 기존 `docs/ai/plan/<id>.md` 가 있으면 초기 / 재실행 / 이어가기를 판단한다.

### 1. planner 호출

`planner` 서브에이전트를 호출한다. planner 는 제품 need 를 프레이밍하고, 코드 영향(파일, 데이터 흐름, 경계면 위험)을 조사하고, 파일별 변경과 단계와 검증과 리스크를 `docs/ai/plan/<id>.md` 에 쓴다.

서버에 보내거나 받는 것이 바뀌면 planner 에게 `quizly-be-contract` 스킬을 먼저 읽으라고 지시한다. **백엔드가 앱에 맞게 개편 중이라 계약이 움직인다.** 기존 웹 클라이언트 코드를 근거로 쓰면 틀린 전제로 계획이 선다.

### 2. plan-critic 호출

`plan-critic` 을 호출한다. 계획과 그 계획이 참조한 코드만 보고(생성자 추론 없이) 가정 오류, 경계면 누락, 범위 이탈, 검증 부족을 찾아 `verdict`(sound / revise / block)로 쓴다.

### 3. 루프

- `sound` -> 승인 게이트로
- `revise` / `block` -> **planner 재호출**("비평의 Critical/Major 반영") -> 재비평

3회를 넘으면 멈추고 사용자에게 보고한다.

### 4. 승인 게이트 (사람 전용)

계획 §1(Context), §2(Non-goals)와 남은 비평 요점을 보여주고 명시적 동의를 받는다. 동의가 있을 때만 frontmatter 를 `status: approved` / `approved: true` / `approved_by` / `approved_at` 로 갱신한다.

**승인 없이는 rh-implement 로 넘어가지 않는다.** builder 가 `approved: true` 를 게이트로 검사한다.

사용자가 인라인 노트를 남기면 planner 를 "노트 전부 반영" 으로 재호출하는 주석 사이클을 돈다.

## 하드 룰

- 이 단계는 소스 코드를 수정하지 않는다.
- 비평자와 planner 는 절대 `approved: true` 를 설정하지 않는다.
- 계획과 비평 산출물은 `<id>` 당 하나.
- **"정상 동작 확인" 같은 문장을 §5 에 통과시키지 않는다.** 누가 무엇을 눌러 무엇을 보면 통과인지 적어야 한다.
- **순수 로직에는 단위 테스트를 요구한다.** 판정 함수, 파서, 포맷터, 계산은 렌더러 없이 전수 테스트가 된다. 수동 확인으로 미루지 않는다.
- **단위 테스트를 요구하는 모듈이 `react-native` 를 import 하면 안 된다.** vitest 가 RN 의 Flow 소스를 파싱하지 못한다. 순수 로직을 RN 비의존 모듈로 분리하도록 계획에 적는다.
- **검증에 태블릿과 폰 두 사이즈를 모두 적는다.** 기준이 태블릿이라 폰이 빠지기 쉽다.
- 실측하지 않은 숫자를 계획에 넣지 않는다. 미확인은 "무엇을 재면 확정되는가" 와 함께 §6 으로.
- 산문은 한국어, 식별자와 경로는 영어. `—` 와 `·` 는 쓰지 않는다.
